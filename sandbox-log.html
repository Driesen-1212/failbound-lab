三、这为什么构成跨环境复现检验

预注册 §10 登记过运行环境分级:沙箱跑预算 200 × 30 种子,本地跑全档 400 × 30 种子,两环境用同一套代码、同一种子派生规则(blake2b)、同一统计口径。

原定的检验方式是:沙箱的 4 个 jsonl 回传本地后执行 compare_environments.py,逐 run 比对 chosen 选择序列。run_one 在给定(任务、策略、种子、数据)之后完全确定性,序列一致即说明代码与数据在两环境逐比特相同。只比汇总统计量,会漏掉数字碰巧一样但路径不同的情况。

我们走的正是这条路,并测出一个修正:上述完全确定性要加上同一浮点环境的前提。换库版本后约六成 run 的轨迹会因近平局决策翻转,定量数据见 §5.5。这不削弱本检验的效力(代码或数据若不同,翻转的会是全部而非六成,且组级统计量与文件级极值指纹仍高度稳定),但逐比特一致的承诺只对 random_uniform 这类没有浮点决策路径的策略成立。

四、需要说明的三点

  1. 沙箱执行跨越约 18.5 小时(10-16 17:08 → 10-17 11:41),因为沙箱单 run 约 25 秒,且 GP 开销随已观测数三次方增长。这不是一次跑完,而是四组顺序执行,每组都有独立的完成验证。
  2. Replay 末尾(12:18–12:25)有一段重复的打包尝试,是沙箱 Agent 在打包环节陷入的循环,不影响已完成的四组数据。该段原样保留,未做剪辑。
  3. 数据交付方式:应我们的要求,沙箱没有暴露 8081 端口,4 个 jsonl 原计划在对话中交付。原因是端口链接依赖沙箱会话存活,而本作品的一条核心主张是可复现不应依赖某个平台还活着,用一个会失效的端口链接交付数据与这条主张矛盾。

5.3 本地数据的一处修复(合并残留)

核对时发现本地 runs_nogate.jsonl 只有 2162 行(1 meta + 2160 run + 1 task_meta),比沙箱结构少 17 行 task_meta。这是 10/17 数据事故恢复时的合并残留,唯一幸存的一行被追加到了文件末尾,内容还是第一个任务的。run 数据 2160 条完整无损,缺的只是元信息头。

修复方式:repair_task_meta.py 按 run_experiments.py 写入时的同一算法再生 task_meta 行。再生算法先在三个完整文件(gate / gate_ablate / nogate_ablate)的 54 行现存 task_meta 上逐字节验证通过,再补齐 nogate 缺失的 17 行(每任务 120 run 后插一条)。修复后 4 个本地文件均为 2179 行,2160 条 run 逐字节未动(有断言保护),原文件已备份为 runs_nogate.jsonl.bak-*。

L5 的意义与边界:max spent 是成本轨迹的指纹。若两侧代码或数据不同,chosen 序列会大规模改变,该值几乎必然漂移,所以它能排除实质性差异。但它不是逐比特指纹:即使代码数据逐比特相同,浮点环境(库版本、BLAS 线程)的差异也会让少量近平局决策翻转。我们后来用全组定量实验(§5.5)把这种环境级敏感性的粒度测到了个位数百分比:换库版本时约六成 run 的轨迹会翻转,但组级统计量差异 ≤2.4%,文件级 max 只在 ±1 个成本单位的带内移动。另需说明,nogate 两组的成本被压平成 1.0(等成本口径,cost_model.cost_vector),每个 run 必然恰好花光 200.0,所以这两行的一致属于结构性恒等,不含轨迹信息;L5 的行为信号全在 gate 两组。

有三点事实需要写清:

  1. random_uniform 是唯一 100% 跨环境稳定的策略(540/540 逐点一致)。它的决策路径是纯 RNG 整数抽样,没有任何浮点运算,这从机理上解释了它为什么零翻转。
  2. farthest_point 与 BO 的轨迹对库版本高度敏感(72%–94% 翻转)。机理由 compare_trajectories.py 逐点定位得到:轨迹前若干步完全一致,随后单个近平局决策被浮点差异打破(BO 是两个候选的 EI/UCB 后验值极接近,farthest_point 是两个候选的最大最小距离极接近),此后训练集与已选集合不同,后续选择蝴蝶效应式发散。分歧之后两环境 chosen 集合的交集只剩 4–5 个点。
  3. 翻转不等于结论翻转。翻转的 run 里,截断 spent 完全相同的占 67%–71%,差 1 个单位的约 16%–20%,差 2 个的约 11%–13%,差 ≥3 个的仅 6/2571 个 run(成本是 1–6 整数,截断值落在 [200, 205] 带内)。

max spent 是 2160 个 run 上的极值统计量。约六成轨迹翻转后分布顶部重新洗牌,它只在 ±1 个成本单位的带内移动。沙箱的两个承诺值都落在这个带内,gate_ablate 的 204.0 还被 B 环境精确复现。它能排除代码与数据的实质性差异(那会让整个分布变形、max 大幅漂移),但不是逐比特指纹,这一点已在上文写明。

线程数也是浮点环境变量,补充登记在此:同一台机器、同一套库,8 线程对生产单线程可使个别 GP run 翻转(抽样 44 个 run 中 1 个,log_gvrh__elem20/gp_ei/7)。生产用单线程(meta 里 n_proc 由 6 降为 1,即 1 线程每进程),sbstack 探针同样单线程,故上表的 A/B 比对已控住线程变量。早前「线程数已排除」的说法只基于 3 个 run,样本不足,现修正为:线程敏感性存在但稀有(约 2% 量级),库版本敏感性常见(约 60% 量级)。

影响评估:

  • 该分歧不触及任何已提交的科学结论。沙箱文件从未参与分析(分析部分在本地做是既定约定),本地分析全部使用预算 400 的全量数据;上面的组级对比进一步表明,即使换成另一套合法浮点环境重跑,结论统计量的变化也在千分位到 2.4% 以内。
  • 跨环境复现的真实粒度现在是实测值:RNG 策略 100% 稳定,FP 敏感策略约四成轨迹稳定、六成翻转但截断行为大多不变(67%–71% 完全相同),组级统计量差异 ≤2.4%,文件级极值指纹在 ±1 成本单位带内。
  • 若沙箱文件日后回传,compare_environments.py 的预期结果已有数字支撑:绝大多数 run 存在浮点级路径分歧(约六成),random_uniform 逐比特一致,聚合统计量吻合。这就是跨环境复现在这个作品里的实际粒度,我们选择定量登记。

六、用提交包重跑(944c87a6)与等价性实证(2026-10-18/19)

6.1 为什么要重跑

第五节的 L1/L2 验证(针对 69c79a06…,67 文件)只能证明沙箱旧包与本地对应文件一致。10-18 复核时发现一个版本门控漏洞:冻结并跑过沙箱的那个包 failbound_full_ablate_upload.zip(SHA256 69c79a06…,5,469,519 字节,67 文件 = 13 个 agent_lab/ + 53 个 data/ + preregistration.md)只是提交版代码包 failbound_full_ablate_upload.zip(SHA256 b6d0a514…,6,698,192 字节,102 文件 = 33 个 agent_lab/ + 62 个 data/ + preregistration.md + 其余新增文件)的严格子集,后者多出 12 个脚本(trial.py / failbound_agent.py / out_guard.py / verify_trial.py / audit_decision_card.py / check_report_consistency.py / compare_environments.py / export_agent_config.py / merge_runs.py / md_to_pdf.py / run_new_tasks.py / screening_demo.py)、8 个 agent 配置导出与 9 个 scan 数据(差异清单按 102 文件口径需重新核验,原 12+8+9=29 项仅覆盖部分新增文件)。

这动摇了第 ② 项(可运行作品链接)的叙事根基:原提交候选 1006bac1… 跑的是 67 文件旧包,与最终要交的 102 文件包不是同一个。

处置方式(用户决策,2026-10-18):用提交包重开干净会话完整重跑,使沙箱执行的包等于提交的包。

三条结论:

  1. 重构数值精确等价。67→102 文件只是把内联逻辑拆成脚本、补导出与 scan 数据,数值核心未动,同包同数据下输出逐比特相同。
  2. 沙箱跨会话确定性可复现。同一四组在两次独立会话(不同容器、相隔约 4 小时)产出除时间戳外完全一致的结果,说明平台执行确定,既非随机,也没有环境漂移到数值层面。
  3. 第 ② 项成立。公开 Replay 链接指向的会话 944c87a6… 确实完整执行了与提交物完全一致的代码包,不存在沙箱跑的子集与提交包脱节的问题。这是 10-18 复核发现并根治的。

说明:第六节的两批结果均产出于 SciencePal 沙箱的同一 Python 3.11 + numpy 2.3.0 / scipy 1.15.3 / sklearn 1.8.0 / pandas 2.3.3 镜像(与本地 §5.5 测定的沙箱同库版本栈一致),故两批之间逐比特一致。若换成另一套浮点环境(如本地默认栈),会触发 §5.5 已量化的约 60% 轨迹翻转,但组级统计量与文件级极值指纹仍在 §5.5 登记的带内。这与本节同环境逐比特一致的结论不矛盾,是不同对照层次下的两个结论。

7.3 S3:包搬得动,但有一个坑

S3 的第一步值得单独写,因为它是这次唯一一个失败过的构建:

  • 第一版包解压后 config._find_data_root() 找不到 holdout/data/tasks, 于是静默回落到错误的 data root,样本外任务数变成 0——不报错,只是跑出空结果。 修法是在 build.py 里显式补 holdout/data/tasks。
  • 冻结包的 config.py 自带 FAILBOUND_PROJECT 开关,本来就是为"代码与数据不同级"准备的; 本方案需要两套数据根(冻结臂 $PWD、样本外臂 $PWD/holdout),正好用这个开关切换, 不去改包内任何一行。
  • 构建末做了一次自查:解出来的 23/23 个 .py 与提交包逐比特相同。 这条比"我改过配置"更有说服力——分析脚本一行没动,所以复算结果才有意义。

S3 样本外重跑已于打包前中止,作为赛后独立复算处理,未计入本次平台提交。 中止原因为沙箱时长限制,样本外 1680 run 未在本平台会话内完成。该发现已登记为可复用的错误恢复经验。本次提交以 S4-a / S4-b / S5 / S7 四个已完成会话与主 Replay 944c87a6 为准,其 16 项跨环境对照全部一致(16 项不含样本外;S3 样本外重跑已中止,未计入)。

7.4 S7 为什么开新会话而不是复用

S7 要测的是"提议者与终裁互不知道对方看到了什么",复用旧会话会让上下文泄漏。所以提议者(d26e70b5)与终裁(ba26fa43)各自独立调用,每回合 2 次调用、18 回合、平均 50 秒/回合,真值只用于打分,从不进 prompt。
